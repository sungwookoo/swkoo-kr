# 후속 개선 및 실제 운영 검증

기준일: 2026-10-28. 앞선 [운영 준비도 점검](./operational-readiness-2026-10-28.md)의 후속 결과다. 검증용 계정·이미지·저장공간만 사용했으며 다른 이용자의 소스 저장소는 수정하지 않았다. 신규 유료 인프라와 사용자 앱 자동 백업은 추가하지 않았다.

이후 같은 날 신규 수용 판단과 변경 충돌 보호를 코드에 반영하고 앱 진단을 추가했다. 현재 결과는 [운영 제어·진단 보고서](./operating-controls-2026-10-28.md)를 우선한다. 아래 수동 승인 기준과 15분 측정은 당시 검증 이력이다.

## 1. GitHub 연결 권한 축소

[PR #83](https://github.com/sungwookoo/swkoo-kr/pull/83)과 [이미지 PR #84](https://github.com/sungwookoo/swkoo-kr/pull/84)로 반영했다. 저장소별 권한을 명시하고 조직 단위 예외는 플랫폼 조직의 생성·목록 조회로 제한했다. 실제 API에서 읽기 토큰의 쓰기 거부, 다른 비공개 저장소 접근 거부, 제한된 생성·보관·삭제와 이미지 조회를 확인했다. 임시 플랫폼 저장소는 삭제했다. [상세 근거](./github-token-scope-2026-10-28.md).

## 2. 실제 로그인 및 상태 저장 앱 전체 흐름

관리자 `sungwookoo`와 일반 `sw-koo`의 실제 브라우저 로그인을 확인했다. 일반 계정으로 관리자 앱에 접근하면 관리 권한 안내가 나오고 관리 패널이 노출되지 않았다. 두 개의 새 일반 계정을 검증했다는 의미는 아니다. 인증 쿠키·비밀번호를 추출하지 않았다.

사용자가 명시적으로 허용한 본인 테스트 저장소 `sw-koo/nextjs-sample`만 [PR #3](https://github.com/sw-koo/nextjs-sample/pull/3)·[PR #4](https://github.com/sw-koo/nextjs-sample/pull/4)로 변경했다. 플랫폼이 다른 이용자의 앱을 자동 수정한 것이 아니다. Next.js·Prisma·SQLite fixture로 실제 ARM64 빌드, 기존 배포 파일 유지 검토, 신규 등록, HTTPS, 빈 DB migration과 환경변수 저장을 확인했다.

합성 기록 1건을 저장한 다음 환경변수 변경에 따른 Pod 교체와 새 소스 빌드에 따른 이미지 교체를 각각 수행했다. 새 화면의 `stateful-v2`, `revision-two`와 기존 기록이 함께 유지됐다. 같은 PVC를 사용했다. 마지막에는 관리 화면에서 테스트 앱을 삭제하고 namespace·Argo Application·PV·실제 저장 디렉터리 회수까지 확인했다. 테스트 소스 저장소와 빌드 이력은 보존했다.

마지막 테스트 이미지 digest는 `sha256:67ea2e481d0f56f6b753a28bdd4e39a090ced22fe66c7222b5667fc72c791535`다. 별도 검증 namespace에서는 다른 PVC 복원, 네트워크 격리와 삭제 후 회수도 통과했다.

## 3. SSR·SQLite 혼합 부하 및 수용 기준

위 테스트 이미지의 독립 앱 3개를 동시에 실행했다. 앱별 상한은 CPU 500m·메모리 512Mi, 예약량은 100m·256Mi이며 각각 독립 1Gi PVC를 사용했다. 요청은 SSR 40%·API 읽기 50%·DB 쓰기 10%로 구성했다. 앱별 1·3·5 요청/초를 15초씩 측정하고, 2 요청/초로 15분 유지했다. 동시에 진행하는 요청은 앱당 2개였다.

총 5,805회에서 오류·누락·컨테이너 재시작은 0건이었다. 지속 구간은 앱당 1,800회였다.

| 임시 앱 | 지속 구간 p95 | 관측 CPU 최대 | 관측 메모리 working set 최대 |
|---|---:|---:|---:|
| A | 12.54ms | 36m | 95Mi |
| B | 12.82ms | 34m | 92Mi |
| C | 12.95ms | 28m | 96Mi |

31회 자원 표본에서 노드 CPU 최대 12%, 메모리 최대 33%였다. 최초 저속 구간의 p95는 약 1.2~1.3초로 초기 지연이 있었다. 지속 구간 수치만으로 모든 요청의 응답 시간을 설명하지 않는다. 측정은 Pod 내부 HTTP를 사용했으므로 외부 네트워크·TLS 지연은 포함하지 않는다. 무거운 SSR 프로젝트나 하루 이상 누수, 임의 사용자 수의 보장 결과가 아니다. 부하 앱과 PVC는 모두 회수했다.

### 초기 운영자 승인 기준

당분간 계정당 앱 1개를 유지하고 신규 계정은 한 번에 하나씩 승인한 뒤 실제 부하를 관찰한다. 승인 전 최근 5분 노드 CPU·메모리 사용률 중 하나라도 70% 이상이면 확대를 보류한다. 신규 예약량과 교체 배포 여유를 계산했을 때 allocatable 대비 미예약 여유가 CPU 1개 또는 메모리 4Gi 미만이 되어도 보류한다. 예약량은 사용량과 별도로 확인한다.

이는 단일 노드의 플랫폼 작업·스캔·교체 배포를 위한 보수적인 초기 운영 판단 기준이며 코드가 자동 강제하는 제한이나 측정으로 입증한 최대 사용자 수가 아니다. 사용 패턴과 장애·지연 기록을 쌓아 조정한다. 자동 증설은 제공하지 않는다.

## 4. 반복 가능한 운영 검증과 화면 수정

[PR #85](https://github.com/sungwookoo/swkoo-kr/pull/85)에 계획 출력/명시적 실행, 대상·이미지·노드·디스크 사전 확인, 시간 제한, 종료 신호 전달, 정리 확인 및 JSON·로그 기록을 추가했다. [실행 절차](./operational-validation-runbook.md)를 따른다. CI에서는 자원 생성 없는 안전성 검사 9개만 실행한다.

실제 통합 실행 결과는 다음과 같다. 시각은 UTC다.

| 사례 | 시작 → 종료 | 결과 |
|---|---|---|
| 혼합 부하 | 07:10:03 → 07:29:18 | passed |
| 저장소·격리·복원·회수 | 07:28:40 → 07:32:41 | passed |
| OOM·자원 대기·DB 시작 실패와 운영 코드 분류 | 07:32:41 → 07:33:07 | passed |
| 의도적 SIGTERM 중단 | 07:34:16 → 07:34:29 | failed로 기록, 남은 namespace 0개 |

마지막 사례는 실패 상태 기록과 정리를 확인하는 중단 시험이며 기대한 결과다. 최초 부하 시도는 신규 Pod 지표가 아직 준비되지 않아 안전하게 중단됐다. 최대 90초 지표 대기를 추가한 뒤 위 부하 시험을 통과했다. SSH 연결이 끊긴 경우 서버의 저장 결과와 실제 자원을 재확인했다.

새 배포 후 스캔 결과와 현재 이미지의 비교 안내가 다음 조회까지 남는 문제도 발견했다. 관리 화면이 보이는 동안 30초마다 비교를 갱신하고, 새로고침 없이 변경되는 브라우저 회귀 검사를 추가했다. 프런트엔드 100개·브라우저 29개·실행기 9개, 백엔드 362개 및 빌드를 통과했다. PR 필수 backend/frontend/smoke 검사도 통과했다.

## 5. 남은 개발 도구 Low

재조회 당시 backend 운영 의존성과 frontend 전체 npm audit는 0건이었다. backend 개발 도구 경로에는 deepmerge Low 공지 1개가 7개 영향 패키지로 남는다. 배포 런타임 의존성에는 포함되지 않는다. 최신 deepmerge 4.3.1도 영향 범위에 있으며 [공식 공지 GHSA-gcqx-w48m-w2h4](https://github.com/advisories/GHSA-gcqx-w48m-w2h4)의 수정 버전은 없다. 구버전 Jest로 강제 다운그레이드하지 않았다. 이 항목은 재확인은 완료했으나 상위 수정판 대기이며 해결 완료로 표시하지 않는다.

## 운영 배포

[PR #85](https://github.com/sungwookoo/swkoo-kr/pull/85)와 [이미지 PR #86](https://github.com/sungwookoo/swkoo-kr/pull/86), [빌드 40651604521](https://github.com/sungwookoo/swkoo-kr/actions/runs/40651604521)로 후속 화면을 반영했다. 운영 backend는 `4aeb2fdca01d8afaf7a7ee4f2397cfa0de89120b`, frontend는 `11eb90a57fdcfbfa08c8432eabdbb0ad7a8761b2`다.

실제 실행 digest의 Trivy 결과는 양쪽 모두 Critical·High·Medium 0건이었다.

| 이미지 | 실행 digest |
|---|---|
| backend | `sha256:9ee5cd7e9472467efe8871d1ce0fcc5cf9ad60c424b877774bc77f7bc4c76426` |
| frontend | `sha256:816fb980571e15e8c84b2506b5c223da94186925b7abf9cb8618b2c0aa9e35b9` |

배포된 frontend를 대상으로 API 응답만 모의 처리한 스캔 비교 브라우저 회귀 검사 1개를 추가 통과했다. 이는 실제 사용자 이미지 변경을 또 발생시킨 검증은 아니다. 실제 Chrome에서 [공개 공지](https://swkoo.kr/notices/2026-10-27-security-update)의 후속 문구도 확인했다. 공지는 내부 구조나 취약점 악용 방법을 공개하지 않는다.

플랫폼 두 Pod Ready·재시작 0, 모든 Argo Application Synced/Healthy였다. 홈·health·공지와 기존 사용자 앱 3개·사용자 custom domain의 HTTPS 응답은 모두 200이었다. 스캔 Job과 검증 namespace·PV는 남지 않았다. 비공개 원본 로그·결과·삭제 전 데이터 보존 화면은 관리 작업 디렉터리에 보관하고 인증 정보는 보고서에 넣지 않았다.
