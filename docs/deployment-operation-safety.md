# 배포 변경 충돌과 신규 등록 수용 기준

현재 단일 backend·Recreate 배포에 맞춘 보호다. 여러 backend replica를 사용하기 전에는 프로세스 내 제외 처리를 공유 저장소 기반으로 바꿔야 한다.

## 변경 요청 충돌

인증 후 `/deploy` 변경 요청과 계정 삭제에 계정별 제외 처리를 적용한다. 등록·앱 삭제·계정 삭제는 공통 등록 Git 브랜치의 기록도 겹치지 않게 처리한다. 겹치는 요청은 `409 OPERATION_IN_PROGRESS`와 재확인 안내를 반환하며 자동으로 대기시키거나 성공으로 간주하지 않는다. 먼저 시작한 작업이 실제로 끝나야 제외를 해제한다. HTTP 연결을 닫아도 실행 중인 작업은 끝날 때까지 보호한다.

같은 앱 재등록은 기존 동의·부분 실패 재시도 절차를 따른다. 다른 앱으로 교체하려면 기존 앱을 먼저 삭제해야 한다. 삭제 중 재등록을 차단하고, 환경변수 변경은 현재 활성 앱에만 허용한다. 외부 GitHub webhook·이미지 갱신·Argo 조정 전체를 잠그는 기능은 아니다. Git SHA 경합 방지와 실제 배포 준비 판정은 계속 적용한다.

## 신규 배포 수용

기존 Prometheus를 읽으며 새 유료 서비스나 자동 증설은 추가하지 않는다. 새로운 앱을 등록하기 전에 다음을 확인한다. 기존 등록 앱의 복구 재배포는 신규 수용 제한에서 제외한다.

- 단일 노드 Ready, MemoryPressure·DiskPressure 없음.
- CPU 최근 5분 rate 사용률 및 메모리 최근 5분 최대 사용률이 각각 70% 미만.
- 실제 예약량에 신규·교체용 200m/512Mi를 더해도 미예약 CPU 1개·메모리 4Gi 이상 유지.
- 디스크는 기존 사용자 PVC 요청량과 신규 1Gi PVC 예산을 공제한 뒤 5Gi 이상 유지한다. 이미 사용한 공간을 중복 공제할 수 있어 보수적이다. PVC별 디스크 상한 강제나 디스크 자동 확장은 아니다.
- 지표 최신성 90초 이내, 충분한 표본, 단일 노드·파일시스템 판정. 조회 실패·누락·모호함은 신규 배포 보류.

일반 컨테이너 요청 합과 init 컨테이너 최대 요청을 비교해 Pod별 예약량을 계산한다. 현재 템플릿은 일반 init 컨테이너만 사용한다. native sidecar init·Pod overhead 등 다른 실행 프로필을 도입하면 수용 계산도 먼저 확장해야 한다. 완료된 작업의 남아 있는 요청까지 집계할 수 있어 일시적으로 보수적으로 보류할 수 있다.

Git 등록 이후 실제 Pod가 나타나기 전의 여유 중복 사용을 막기 위해 `admission_reservations`에 계정별 예약을 남긴다. 재시작·동일 계정 재시도에도 한 번만 계산한다. 같은 지표 스냅샷에 해당 namespace의 요청이 들어오면 예약을 해제하고 실제 예약량으로 계산한다. 정상 앱 삭제에서도 해제한다. 부분 실패·결과 불명 시 시간만 지나서 자동 해제하지 않는다.

## 남은 예약 확인과 해제

예약은 운영 DB의 `admission_reservations(login, created_at)`에서 확인한다. 운영자가 임의로 일괄 삭제하지 않는다. 대상의 등록 파일, Argo Application, namespace와 PV, 진행 중 변경이 없는지 확인하고 부분 배포가 남았다면 기존 삭제·재시도 절차로 먼저 해결한다. 자원이 없고 더 이상 생성될 등록도 없음을 확인한 대상 한 건만 해제한다. 계정 삭제 시 남은 예약의 login은 익명 식별자로 바뀌므로 운영 감사 기록과 함께 확인한다.

이 기준은 새 등록의 과밀 위험을 낮추는 보호이며, 기존 앱이 동시에 최대 자원을 사용하는 상황이나 특정 사용자 수·SLA를 보장하지 않는다. 기본 앱 상한 500m/512Mi·예약 100m/256Mi는 유지한다. 다른 이용자의 소스 저장소는 변경하지 않는다.
