# 사용자 배포 흐름·계정 간 권한 검증 (2026-10-28)

## 1차 검증 범위

- 사용자 저장소를 수정하지 않고 플랫폼 코드와 검증용 데이터만 사용했다.
- 브라우저에서는 API를 대체한 상태 기반 시나리오로 저장소 선택 → 변경 동의 → 배포 등록 → 진행상황 → 환경변수 저장 → 새로고침 → 삭제 취소/확정을 연결했다.
- 기존 브라우저 시나리오로 미로그인·권한 없음·지원하지 않는 앱·사전 점검 실패·GitHub App 설치 누락·빌드 실패·등록 중 부분 실패·소스 변경 PR 검토를 확인했다.
- 운영 백엔드에서는 별도 검증 사용자 두 명과 만료되는 세션, 전용 namespace의 작은 검증 앱만 사용했다. 실제 GitHub OAuth 로그인은 수행하지 않았다.

## 발견 및 수정

1. `PUT /deploy/env/:login/:repo`가 `vars: []`를 빈 객체처럼 처리해 기존 환경변수를 비울 수 있었다. 배열은 HTTP 400으로 거부하고 기존 Secret을 유지한다. 명시적인 `vars: {}`를 통한 전체 삭제는 계속 지원한다.
2. 배포 권한을 회수한 사용자가 기존 세션으로 본인 환경변수를 변경할 수 있었다. 저장 시 현재 사용자 권한을 확인해 HTTP 403으로 거부한다.

두 경우 모두 환경변수 서비스 호출 이전에 거부하는 회귀 테스트를 추가했다.

## 검증 근거

- 백엔드: 31개 suite, 335개 테스트 통과 및 TypeScript 빌드 통과.
- 브라우저: 기존 20개 시나리오 통과, 새 연결 시나리오 1개 통과. 실제 API를 호출하는 테스트와 구분한다.
- 환경변수 서비스 테스트: 사용자별 Secret 분리, 생성/교체/전체 삭제, 저장 시 재시작 요청, 잘못된 키의 무변경 거부, 감사 기록에 값 미포함을 확인한다.
- 운영 HTTP: 각 검증 사용자의 본인 환경변수 저장/조회 성공, 상대방 상태/환경변수/도메인 조회 및 변경 거부, 상대방 저장소 배포/보안 수정안 요청 거부, 임의 userId를 붙여도 본인 스캔만 반환, 로그아웃한 세션 재사용 거부를 확인했다.
- 실제 검증 앱: 환경변수 저장으로 시작된 rollout 완료 후 프로세스가 변경된 값을 읽는 것을 확인했다.
- 검증용 사용자·세션·스캔·감사 데이터는 실행 종료 시 정리한다. 전용 namespace와 앱도 검증 종료 후 제거한다.

## 1차 검증 한계

GitHub Actions 빌드부터 GitOps 등록·공개 도메인 발급·삭제까지를 신규 실제 GitHub 계정 두 개로 통과하는 종단 검증은 이번 결과에 포함하지 않는다. 기존 사용자 배포를 교체하거나 다른 사용자 저장소를 변경하지 않기 위해, 해당 경계는 기존 서비스 테스트와 API를 대체한 브라우저 테스트로 검증했다. 운영 계정의 인증 쿠키·GitHub 토큰을 출력하거나 복사하지 않았다.

## 후속: 실제 GitHub 세션으로 전체 배포 흐름 검증

사용자가 Chrome의 일반 계정 `sw-koo` 세션 사용과 기존 테스트 앱의 삭제·교체를 허용했다. 기존 앱 복원은 필요 없다는 지시에 따라 검증 완료 후 배포는 삭제했다. 이 단계의 서비스 화면과 GitHub 요청은 대체 API를 사용하지 않았다.

| 단계 | 실제 확인 결과 |
| --- | --- |
| 로그인 | Chrome의 기존 GitHub 세션으로 swkoo.kr OAuth 로그인 성공 |

| 기존 앱 삭제 | 등록 파일 제거, deploy 저장소 보관 처리, Application·namespace 제거 확인 |
| 소스 변경 검토 | 화면에서 Dockerfile·workflow 차이 확인 후 초안 PR 생성. 별도 검토·병합 후 기본 브랜치 기준 SHA 재조회 |

| 이미지·컨테이너 | 새 commit `93e6f5e88a6f283d17f10ae36ba6ae55acea4894`의 digest와 실제 운영 이미지 일치 확인. 진행도 5단계 모두 완료 |

| 환경변수 | 화면에서 검증용 값 저장, rollout 완료, 실행 프로세스에서 동일한 값 확인. 새로고침 후 값이 가려진 상태로 유지 |
| 로그아웃·복귀 | 로그아웃 후 기존 관리 주소에서 로그인 안내만 표시. 재로그인하면 원래 주소로 돌아와 관리 가능 |
| 스캔 상세 | 실제 계정의 상세 결과 열림. 과거 이미지 결과가 현재 이미지와 다르다는 안내 표시 확인 |
| 최종 삭제 | 최종 수정 이미지에서 삭제 실행. 수동 갱신 없이 Application·namespace 제거, 등록 목록에서 제외, deploy 저장소 보관 처리 확인 |

검증한 앱 이미지 digest는 `sha256:316c080418538bdc8f1146e108255a62bd1d3d5bb98d7708b9f6057361d6db72`다. 환경변수 저장 전후 공개 페이지의 컨테이너 hostname 변경도 확인했다. 최종 namespace 삭제로 해당 앱의 컨테이너·인증서·환경변수 Secret이 함께 제거됐다. 테스트 소스 저장소와 GitHub 이미지 이력은 보존했다.

### 실제 검증에서 발견한 추가 문제와 수정

1. 코드 저장소의 PR·필수 검사 보호 규칙 때문에 `main`에 직접 기록하던 배포 등록·삭제가 실패했다. 기존 네 등록 파일과 동일한 내용을 별도 `deployment-data` 브랜치에 먼저 준비하고 백엔드와 ApplicationSet을 전환했다. `main` 보호 규칙은 유지했다. GitHub ref 갱신 실패는 설치 토큰을 포함한 Axios 객체 대신 안전한 HTTP 오류로 반환한다. [플랫폼 PR #75](https://github.com/sungwookoo/swkoo-kr/pull/75)
2. Application용 갱신 annotation을 ApplicationSet에 사용해 즉시 갱신 요청이 동작하지 않았다. ApplicationSet 전용 annotation으로 수정하고 최종 삭제에서 수동 개입 없이 반영되는 것을 확인했다.
3. 신규 namespace 준비 중 환경변수 API가 권한 오류를 반환하면 화면이 불필요한 재배포를 권했다. 준비 중에는 기다리도록 안내하며, 실제 완료/실패 상태의 권한 복구 안내는 유지한다. [플랫폼 PR #77](https://github.com/sungwookoo/swkoo-kr/pull/77)

최종 플랫폼 코드 이미지 기준은 `5c9d22348d1825dccda53035980c1a3a8db8d834`이며 backend/frontend rollout을 확인했다. 백엔드 341개·프런트엔드 95개 테스트 및 브라우저 21개 시나리오가 CI에서 통과했다. 배포는 [PR #78](https://github.com/sungwookoo/swkoo-kr/pull/78)로 반영했다.

다른 사용자 소스 저장소는 변경하지 않았다. 허용받은 테스트 저장소에서 변경한 파일은 Dockerfile과 빌드 workflow 두 개다. 나머지 세 사용자 앱은 최종 확인에서 모두 Synced / Healthy였다.

### 남는 검증 범위

이번 실제 OAuth 전체 흐름은 일반 계정 한 개로 수행했다. 서로 다른 두 계정의 신규 OAuth 로그인 전체 수행, 상태 저장 앱의 DB 보존·삭제, 외부 보안 침투시험까지 확인한 결과는 아니다. 사용자 간 양방향 API 차단은 앞선 HTTP 테스트로 검증했고, 실제 일반 계정에서는 관리자 앱 접근 거부를 추가 확인했다. 인증 쿠키·비밀번호·GitHub 토큰을 추출하거나 공유하지 않았다.

## 반복 실행

```powershell
cd apps/backend
npm test -- --runInBand
npm run build
cd ../frontend
npm run test:e2e
```

브라우저 기본 설정은 로컬 3100 포트를 사용한다. 다른 앱이 그 포트를 점유하면 전용 포트와 동일한 `NEXT_PUBLIC_API_BASE_URL`을 지정한 별도 Playwright 설정을 사용한다.
