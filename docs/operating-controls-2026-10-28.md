# 배포 운영 제어와 사용자 진단 검증

기준일: 2026-10-28. [앞선 후속 점검](./platform-followup-2026-10-28.md) 이후 요청한 우선순위 1~5를 진행했다. 현재 운영 제어는 이 문서와 [STATUS](./STATUS.md)를 기준으로 한다. 다른 이용자의 소스·배포 저장소는 수정하지 않았다. 기존에 허용받은 테스트 계정의 등록·삭제와 기존 테스트 이미지 재사용만 수행했으며 테스트 소스 커밋 `dcab0b500721f31d74ad22b8132ffa2f0a5065cc`도 유지했다. 신규 유료 인프라·사용자 앱 자동 백업은 추가하지 않았다.

## 1. 변경 요청 충돌 방지

[PR #88](https://github.com/sungwookoo/swkoo-kr/pull/88)로 인증된 계정의 등록·환경변수·도메인·앱 삭제·계정 삭제가 겹치지 않도록 했다. 공통 Git 등록 브랜치에 쓰는 작업도 직렬로 처리한다. 겹치는 요청은 409와 현재 상태 확인·재시도 안내를 반환한다. HTTP 연결이 끊겨도 실제 작업이 끝날 때까지 보호한다. 실패 뒤에는 제외를 해제해 재시도할 수 있다.

현재 등록 앱을 다른 앱으로 덮어쓰는 요청, 삭제 중 재등록, 현재 앱이 아닌 환경변수 변경을 거부한다. HTTP 통합 시험에서 중복 요청이 추가 Git/환경변수 쓰기를 실행하지 않는지 확인했다. 이는 현재 단일 backend·Recreate 구조에 맞춘 제어이며 여러 replica·외부 webhook·GitHub에서 직접 수행한 변경 전체에 대한 분산 잠금은 아니다. [설계와 복구 절차](./deployment-operation-safety.md).

## 2. 신규 배포 전 수용 판단

현재 사용량과 실제 예약량, init 요청, 노드 상태와 디스크를 기존 Prometheus에서 확인한다. CPU 70%·메모리 70%, 미예약 CPU 1개·메모리 4Gi 여유, 기존 사용자 PVC 요청량과 신규 1Gi 디스크 예산 공제 후 5Gi 여유를 기준으로 보류한다. 이미 사용한 공간을 중복 공제할 수 있는 보수적 기준이다. 누락·오래된 지표·연결 실패는 신규 등록을 진행하지 않는다. 새 앱과 교체용 200m/512Mi 예약분을 아직 Pod가 나타나지 않은 등록에도 반영하고 SQLite에 보존한다. 기존 등록 앱의 복구 재배포는 이 신규 수용 제한에서 제외한다.

수용 예약은 같은 스냅샷의 실제 요청으로 확인하거나 정상 삭제한 뒤 해제한다. 시간만 지나서 미확인 예약을 없애지 않는다. 본인 계정 데이터 내보내기에 본인의 예약 정보만 포함하며 계정 삭제 시 미확인 예약은 익명 식별자로 바뀐다. CPU·메모리 상한과 예약 기본값은 각각 500m/512Mi, 100m/256Mi로 유지했다.

실제 신규 등록에서 발견한 문제도 수정했다. 프로젝트를 지정하지 않은 Argo 조회는 없는 앱에도 403을 반환할 수 있다. 사용자 ApplicationSet의 `default` 프로젝트를 명시해 실제 부재 404와 권한 오류 403을 구분했다. 실제 403·연결 오류를 부재로 취급하지 않는다. [공식 동작](https://argo-cd.readthedocs.io/en/stable/developer-guide/api-docs/#how-to-avoid-403-errors-for-missing-applications), [PR #90](https://github.com/sungwookoo/swkoo-kr/pull/90).

수정 후 실제 일반 계정으로 신규 등록·전체 배포 준비·HTTPS·환경변수 저장을 통과했다. 등록 전 예약 행 생성, 삭제 후 예약 없음, namespace·PV·실제 저장 디렉터리 회수를 확인했다. 소스 파일은 유지됐고 빌드 이력도 기존 커밋의 것을 사용했다. 수용 제어가 특정 최대 사용자 수나 모든 앱의 동시 최대 사용을 보장하는 것은 아니다.

최종 검토의 기존 PVC 예산 공제 보강은 [PR #94](https://github.com/sungwookoo/swkoo-kr/pull/94)로 적용했다. 검증 앱이 포함된 당시 지표에서 사용자 namespace의 PVC 요청량 4Gi를 읽었고 운영 지표로 별도 판정 시험을 통과했다. 이 시험은 예약 기록을 대역으로 처리해 운영 DB에 쓰지 않았다. 부족·누락 경계 회귀 검사도 포함했다. 최종 운영 이미지에서도 같은 계산을 실제 지표로 실행하고, 예약 기록을 대역으로 처리한 별도 판정을 통과했다.

## 3. 외부 HTTPS 장시간 검증

Windows 관리 PC에서 공개 HTTPS 주소를 직접 호출했다. 독립 Next.js/Prisma SQLite 앱 3개에 앱별 1·3·5 요청/초를 각각 15초씩 보낸 뒤, 2 요청/초로 3,600초 유지했다. SSR 40%·API 읽기 50%·DB 쓰기 10%, 앱당 동시 요청 최대 2개였다. 각 앱은 500m/512Mi 상한·100m/256Mi 예약·독립 1Gi PVC를 사용했다.

총 **22,005회**, 오류·누락·컨테이너 재시작 **0건**이었다. 지속 구간은 앱당 7,200회이며 DB 기록은 각각 735건으로 예상 쓰기 수와 일치했다.

| 앱 | 지속 구간 p95 | 전체 관측 CPU 최대 | 전체 관측 메모리 working set 최대 |
|---|---:|---:|---:|
| A | 46.68ms | 33m | 88Mi |
| B | 48.61ms | 27m | 90Mi |
| C | 49.81ms | 45m | 90Mi |

103회 표본에서 노드 CPU 최대 23%, 메모리 최대 33%였다. 측정 중 플랫폼 배포·점검과 별도 테스트 앱 검증도 함께 진행했다. 준비·정리를 포함한 실행은 17:28:04~18:33:35 KST였다. 최초 시도는 인증서 발급 완료와 Ingress 반영의 시간차로 TLS 검증에 실패해 정리됐다. 검증 해제 없이 정상 HTTPS까지 기다리도록 보완한 후 위 전체 시험을 통과했다.

종료 후 검증 namespace·PV·실제 저장 디렉터리 3곳이 남지 않았음을 별도로 확인했다. 다른 이용자의 앱은 부하 대상에 포함하지 않았다.

측정 전에 기동·TLS를 확인하므로 신규 빌드·migration 시간이나 첫 기동 성능은 포함하지 않는다. 응답 문서/API를 측정했으며 브라우저 자산 다운로드·화면 렌더링, 무거운 임의 SSR 프로젝트, 하루 이상 누수나 최대 사용자 수를 보증하지 않는다. 실행기 결과에서 임시 namespace 0개를 확인했다.


별도의 일반 계정 테스트 앱에서는 두 요청씩 20쌍, 총 40건의 동시 HTTP 쓰기를 수행했다. 오류 0건, DB 기록 0→40, 고유 값 40개를 확인했다. 여러 앱이 같은 DB 파일을 공유하거나 다중 replica에서 쓰는 시험은 아니다. 이 앱은 아래 실제 진단 검증 후 삭제했다.

## 4. 본인 앱 사용량과 요청형 로그

관리 화면에 실제 컨테이너 상한과 최근 CPU·메모리 관측값, 재시작 횟수를 추가했다. 지표가 없으면 측정 대기로 표시하고, 준비되지 않은 컨테이너나 초기화 실패를 정상 실행으로 표시하지 않는다. 로그는 요청할 때만 최근 1시간·100줄·16KiB 범위에서 조회한다.

서버는 인증 계정·접근 허용·현재 활성 저장소를 확인한다. 원문 환경변수 값과 일반 인증 형식을 가리고, 환경변수 조회 실패 시 원문 로그를 내보내지 않는다. 임의 로그의 모든 민감정보 탐지를 보증하지 않으며 화면에 공유 전 확인을 안내한다. `no-store`, HTML 텍스트 렌더링, 내용 없는 감사 기록을 적용했다. [범위와 운영 이행](./app-diagnostics.md).

기존 활성 사용자 namespace 3개에 `get pods/log`만 가진 별도 Role·RoleBinding을 이행했다. 다른 사용자 저장소와 기존 GitOps Role은 수정하지 않았다. 해당 namespace의 로그 읽기는 허용되고 `kube-system` 로그 읽기와 사용자 Pod 실행 권한은 거부됨을 확인했다. 다른 이용자의 실제 로그는 읽지 않았다.

실제 일반 계정 관리 화면에서 사용량과 상한, 로그 조회를 확인했다. 테스트 전용 값과 인증 헤더를 해당 테스트 앱 stdout에 넣고 화면에서 `[숨김]`으로 반환되는 것을 확인했다. 감사 기록에는 `APP_LOG_VIEW`와 앱 이름만 남았다. 다른 계정의 관리 화면은 권한 안내만 표시하고 진단·환경변수·로그 패널을 노출하지 않았다. 이후 앱·Secret·DB 저장공간과 예약을 삭제했다.

## 5. 개발 도구 Low 재확인

최신 deepmerge는 조회 시점 4.3.1이며 [GHSA-gcqx-w48m-w2h4](https://github.com/advisories/GHSA-gcqx-w48m-w2h4)의 공식 수정판은 여전히 없다. backend 개발 도구 경로의 Low 1개 공지가 7개 영향 패키지로 집계되며 구버전 Jest 강제 다운그레이드나 비공식 패치는 하지 않았다. backend 운영 의존성과 frontend 전체 npm audit는 0건이었다. 이 항목은 수정판 대기이며 해결 완료로 표시하지 않는다.

## 테스트와 운영 배포

backend 407개, frontend 100개, 브라우저 회귀 30개, Python 안전성 12개와 네트워크 없는 클라이언트 정체 중단 검사, 양쪽 빌드를 통과했다. 브라우저 회귀의 API 대역 시험과 위 실제 서비스 검증은 구분한다. 외부 검증 클라이언트는 동시 요청 상한에서 누락을 계속하지 않고 즉시 중단하도록 보강했다. [PR #92](https://github.com/sungwookoo/swkoo-kr/pull/92).

배포 PR은 [#89](https://github.com/sungwookoo/swkoo-kr/pull/89)·[#91](https://github.com/sungwookoo/swkoo-kr/pull/91)·[#93](https://github.com/sungwookoo/swkoo-kr/pull/93)·[#95](https://github.com/sungwookoo/swkoo-kr/pull/95)다. 최종 backend 코드 이미지는 `ea10956485cbfe0e4c749282f6e66e521b80d17d`, frontend는 `7992d3b801ec7b112588b19fd2bb902ae72a122c`다.

실행 digest는 backend `sha256:3b3cd3b18ab158936ea39d0cfbf877917745aa593c08fa3d8073a29bae896519`, frontend `sha256:bf083a57dbfe42a906da8a031aff67240bd7058ffc31b9083497ffdb924370cf`다. 이 digest를 실제 Trivy Job으로 검사해 양쪽 Critical·High·Medium 0건을 확인했고 검사 Job은 제거했다. Low 전체가 없다는 결과로 확대하지 않는다.

최종 이미지에서 양쪽 Pod Ready·재시작 0, 모든 Argo Application Synced/Healthy를 확인했다. 홈·health·공지와 기존 앱 3개·사용자 custom domain 모두 정상 TLS 검증으로 HTTPS 200이었다. 배포된 frontend를 대상으로 모의 API 브라우저 검사 6개도 통과했다. 실제 관리 화면·로그 검증과 별개로 API 응답 변화에 대한 UI 회귀 검사다. 공개 공지에는 충돌 보호·서버 여유 확인·본인 앱 실행 정보 개선만 간단히 안내했다.
