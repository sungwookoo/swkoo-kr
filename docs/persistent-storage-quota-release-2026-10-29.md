# 영구 저장공간 1GiB 강제 제한 운영 적용 보고서

적용일: 2026-10-29 (KST). [기능 PR #100](https://github.com/sungwookoo/swkoo-kr/pull/100), [운영 이미지 PR #101](https://github.com/sungwookoo/swkoo-kr/pull/101)을 통해 운영 반영과 시험을 완료했다. 사용자 앱의 정기 백업과 새 유료 클라우드 리소스는 추가하지 않았다.

## 결과

이전에는 PVC에 `1Gi`를 요청해도 기본 local-path provisioner가 실제 쓰기 한도를 강제하지 않았다. 운영 데이터 ext4 볼륨에 project quota를 적용하고, 신규 Prisma SQLite 앱은 전용 `swkoo-user-quota` 클래스로 생성한다. 디렉터리별 실제 할당량 1GiB와 inode 65,536개를 제한하며, 한도에 도달하면 추가 쓰기를 거부한다. 기존 파일을 자동 삭제하지 않는다.

기존 SprintFlow PVC의 클래스·경로·데이터를 유지한 채 같은 한도를 적용했다. 플랫폼 DB·Prometheus·스캔 캐시·Portainer 등 플랫폼 볼륨에는 앱별 한도를 적용하지 않는다. 기존 `local-path` 클래스도 유지한다. 앱의 CPU·메모리 상한 500m·512MiB 및 예약량 100m·256MiB는 이번 작업에서 변경하지 않았다.

사용자 파일 소유자가 프로젝트 속성을 바꾸어 제한을 우회하지 못하도록 stateful Pod의 seccomp 설정을 보강했다. 새 볼륨 생성 시 제한 기능을 확인하지 못하면 보호 없는 볼륨을 대신 생성하지 않는다. 데이터 볼륨의 UUID·마운트·quota 활성화·보안 프로필 해시를 K3s 시작 전에 확인한다.

## 복구 사본과 데이터 보존

- 먼저 SQLite backup API로 업무 DB 사본을 만들고 PC에서 복호화·복원해 backend와 SprintFlow 모두 `PRAGMA integrity_check=ok`를 확인했다.
- 별도의 시험용 loop 디스크를 전체 블록 이미지로 복제하고 CRC를 검사했다. 디스크 기능과 DB를 바꾼 뒤 원래 이미지로 복원하여 DB 해시·무결성·원래 파일시스템 기능이 모두 복구되는지 확인했다.
- 운영 쓰기를 정상 종료한 후 디스크를 정상 해제하고 오프라인 파일시스템 검사를 통과했다. 포맷하지 않았다.
- 변경 직전 전체 사용 블록을 partclone으로 복제하고 전송 중 CRC 검사, PC의 AES-GCM 인증 복호화와 gzip CRC 검사를 완료한 뒤에만 파일시스템을 변경했다. 일회성 최종 암호화 사본은 **2,475,757,367바이트**, 이미지 원본 스트림은 **13,695,052,914바이트**다.
- 최종 암호화 사본 SHA-256: `d6224a2f46296b77494cbd479b6bb1650631a95e4be1555ee5d301b0afe64a10`.
- 키는 현재 Windows 사용자 DPAPI로 보호하고 사본은 접근 제한된 운영자 PC 폴더에 보관한다. 원래 배포 수·fstab·PV/PVC 등 제어 정보 사본도 별도로 보존한다. 먼저 만든 온라인 전체 파일 사본은 보조 자료이며, 최종 오프라인 블록 사본이 이번 전환의 복구 기준이다.
- 쓰기 재개 전 기존 PV 파일 **91개 전체의 SHA-256이 변경 전과 일치**했다. 서비스 재개 후 두 DB의 무결성도 다시 `ok`였다. 원래 PV 6개의 UID를 모두 보존했다.

쓰기 재개 이후에는 과거 블록 사본을 그대로 덮어쓰지 않는다. 새로 저장한 데이터를 보존하는 별도 복구 절차가 필요하다. 일회성 사본은 정기 백업 서비스를 의미하지 않는다.

## 실제 중단과 복구

외부 PC에서 약 5초 간격으로 HTTPS 상태를 383회 관측했다. 아래 시간은 HTTP 관측 기준이며 요청·관측 간격만큼 오차가 있다.

| 대상 | 관측된 중단 구간 (KST) | 소요 |
| --- | --- | --- |
| 플랫폼 API | 14:09:13 ~ 14:21:32 | 약 12분 19초 |
| SprintFlow | 14:09:13 ~ 14:20:49 | 약 11분 36초 |
| 메인 페이지 | 오류 관측 없음 | HTTP 200 유지 |
| PocketPlan·Portfolio | 오류 관측 없음 | HTTP 200 유지, 컨테이너 재시작 없음 |

Argo 동기화·작업 생성기를 잠시 멈추고, 보조 저장 서비스부터 종료한 다음 API·SprintFlow를 종료했다. 원래 배포 수 9개 항목과 자동 동기화·스케줄링 상태를 복구했다. 최종 Argo 애플리케이션 10개는 모두 `Synced/Healthy`였다. 추가 서비스 중단을 피하려고 실제 인스턴스 재부팅은 하지 않았으며, 격리 디스크 재마운트 시험과 운영 시작 전 보호 검사·fstab·현재/다음 부팅 커널의 quota 모듈을 확인했다.

일반 계정 `sw-koo`의 기존 시험 앱도 실제 서비스 흐름으로 신규 등록했다. `swkoo-user-quota` PVC가 자동 생성됐고 1GiB·65,536개 제한과 프로젝트 상속을 확인했다. 실제 앱의 비특권 프로세스가 파일을 쓰다가 **1,073,713,152바이트에서 OS의 EDQUOT**를 받았다. DB 등 이미 사용 중인 공간 때문에 파일 하나가 정확히 1GiB까지 커지는 것은 아니다. Node에서는 이 오류가 `UNKNOWN`과 숫자 errno `-122`로 나타나므로 시험은 OS errno도 확인했다.

시험 파일을 지운 뒤 새 기록 저장이 가능했고, Pod를 교체한 후에도 기록 2개와 DB 무결성이 유지됐다. 앱 화면에서도 두 기록을 확인했다. 제거 기능 실행 후 Application·namespace·PV·물리 디렉터리가 없어지고 quota 사용량과 한도가 모두 0으로 회수됐다. 시험 namespace·PV·loop 디스크도 정리했다.

모니터링 재개 직후에는 새 관측값이 충분하지 않아 신규 등록이 일시 보류됐고, 필요한 표본이 쌓인 뒤 정상 등록됐다. 수용 검사 기준을 낮추거나 우회하지 않았다.

## 저장소 변경과 안내

- 다른 이용자의 소스·배포 저장소는 수정하지 않았다. 운영자 소유 SprintFlow의 플랫폼 배포 설정에서 Pod 보안 프로필만 변경했다.
- 허용된 시험 계정의 배포 등록·삭제는 플랫폼이 관리하는 등록 정보와 생성 매니페스트를 변경했다. 시험 앱의 **소스 저장소**는 전후 모두 `dcab0b500721f31d74ad22b8132ffa2f0a5065cc`로 유지됐다. 새 소스 빌드를 유발하는 수정은 하지 않았다.
- 배포 화면·시작 안내·약관에 실제 영구 저장 한도와 도달 시 저장 오류를 명시했다. [공개 공지](https://swkoo.kr/notices/2026-10-29-storage-update)에는 이용자에게 필요한 범위만 안내하고 기존 메인의 공지 링크를 유지했다.
- 현재 backend/frontend 실행 source revision은 모두 `6617a2e69ca5ce0c9b4fbadff427572135c0b98c`, 이미지 manifest commit은 `9d832cce30a39c0510301530bf4926fe431f8adb`다.

최종 ARM64 실행 관리 이미지:

- helper: `sha256:5bab48732aa3060e539c60584ed90cacdf9f7b33b6e4bb61c907c4613f1f0b87`

## 유지보수 범위

반복 절차와 복구 경계는 [운영 절차](./persistent-storage-quota-runbook.md)를 따른다. 커널 변경 시 quota 모듈, K3s/containerd 변경 시 seccomp 기준을 다시 확인한다. 기존 이미지 정리는 ConfigMap·일시적인 helper 참조를 모두 수집하지 못하므로 새 storage 이미지 태그는 삭제 대상에서 제외했다.

한도는 실제 할당 블록과 inode 기준이며 `df`가 표시하는 전체 디스크 크기와 다르다. DB journal/WAL도 포함하므로 여유 공간과 앱의 저장 실패 처리가 필요하다. 이번 검증은 지원되는 SQLite 프로필과 단일 노드 운영 범위이며 모든 앱의 동작·무중단·정기 데이터 복구를 보장하지 않는다.
