# 플랫폼 운영 후속 점검 — 2026-11-12

## OCI 저장공간과 플랫폼 DB

- 11월 4일 배포 뒤 자동 백업이 누락됐고 11월 12일 05:10 KST 정리는 최근 백업을 확인할 수 없어 삭제 전에 중단됐다. 기존 코드는 백엔드 시작 시 OCI 인증을 한 번만 시도했고, 실패하면 이후 예약 백업도 건너뛰었다. 배포 당시 새 컨테이너 시작과 호스트의 OCI 접근 허용 갱신 시차를 확인했다. 당시 초기화 오류 원문은 로그에서 확보하지 못했다.
- 11월 12일 17:03 KST에 기존 백업 서비스로 운영 플랫폼 SQLite의 온라인 사본을 생성했다. OCI에서 받은 사본의 SHA-256, SQLite 무결성, 외래 키 검사를 통과했다. 이후 기존 보관 정책을 다시 실행해 만료 백업 7개를 정리했다. 이미지 삭제 0개, 보관 백업 7개, OCI 이미지와 백업 합계 1,727,486,796바이트로 8GB 예산 이내다.
- OCI 비용 API의 11월 1일부터 12일 09:00 KST까지의 집계는 SGD 0이다. 조회 후의 비용은 추후 반영될 수 있다.
- 백업을 실행할 때 인증하고 실패하면 다음 실행에서 다시 인증하도록 수정했다. 실패 감사 로그와 기존 보관 중단 조건을 유지한다. 운영 반영 후 04:00 KST 자동 백업과 05:10 KST 정리를 각각 확인해야 한다. 수동 백업만 실행한 상태에서는 이후 백업이 계속 누락될 경우 48시간 보호 조건이 다시 작동한다.

## API 교체 및 의존성

- 이전 API 교체에서 약 30초는 기존 서비스 엔드포인트 변경부터 새 백엔드 저장공간 준비까지였다. 새 컨테이너 준비는 약 1.6초였고, 그 이후 공개 API가 정상화되기까지 약 22초가 더 걸렸다. 기존 컨테이너가 시간을 소비한 정확한 이유는 확인하지 못했다.
- 다음 이미지 반영 PR에서 백엔드의 readiness 초기 대기를 제거하고 검사 주기를 10초에서 2초로 조정한다. 매니페스트 렌더링을 검증했다. 이미지 버전과 한 번에 반영해 백엔드 교체가 두 번 발생하지 않도록 한다. 단일 백엔드 및 종료 유예를 유지하고 공개 health로 실제 교체 시간을 재측정한다.
- Node 24.22.3으로 ARM64 Alpine에서 운영과 같은 SQLite 네이티브 모듈의 쓰기, WAL 스냅샷, 무결성, 다시 열기와 정상 프로세스 종료를 확인했다. 전체 CI와 컨테이너 검증을 거쳐 적용 여부를 결정한다.
- 프런트엔드 개발 도구의 minimatch 10 계열만 11.0.1로 고정했다. ESLint와 Next 설정을 로드해 TypeScript 파일의 glob 선택을 확인했다. 프런트엔드 전체 npm audit와 백엔드 운영 npm audit는 각각 0건이다. 백엔드의 Jest 설정 경로에는 수정 버전이 없는 [deepmerge Low 공지](https://github.com/advisories/GHSA-gcqx-w48m-w2h4)가 남아 있다.

## OCI 인스턴스 재부팅 검증 절차

운영자와 합의한 점검 시간에 진행한다. 단일 인스턴스이므로 재부팅 동안 플랫폼과 사용자 앱이 함께 중단되며, 실제 중단 시간은 외부에서 측정한다. 앱 이미지 배포와 별도 단계로 기록한다.

1. 점검 전 최신 플랫폼 DB 백업을 검증한다. 진행 중인 신규 배포·삭제 및 복구 작업이 없는지 확인한다. 플랫폼·사용자 앱 외부 응답, 노드·Argo 상태, PV UID, 부팅 ID를 기준으로 기록한다.
2. `findmnt --verify`와 `sudo /usr/local/sbin/swkoo-storage-preflight`가 통과하고, K3s가 `/data`와 스토리지 마운트를 요구하는지 확인한다. 11월 12일에는 모두 통과했고 두 경로의 ext4 `prjquota`가 활성 상태였다.
3. OCI 콘솔 접속 경로를 확보하고 OS에서 정상 재부팅한다. 외부에서 사이트, API, 대표 앱의 중단과 복구 시점을 기록한다.
4. 새 부팅 ID를 확인한다. 두 마운트, 시작 전 검사와 K3s, Argo, PV UID, 앱과 플랫폼 HTTPS, 저장공간 수집과 OCI 정리 타이머를 비교한다. 할당량 쓰기 시험이 필요하면 전용 시험 데이터로만 진행한다.
5. 저장공간 검사 실패 시 K3s의 시작 차단을 유지한다. OCI 콘솔에서 대상 볼륨·마운트·프로필을 확인해 복구한 뒤 사전 검사 통과를 확인하고 K3s를 시작한다.
