01 · 신규 개발2025.12–현재
성적산출 시스템

성적산출 시스템을 웹으로

요구사항 정리·설계·구현을 맡아 개발한 시스템이 가천대학교 포함 4개 대학의 실제 입시에 사용되고 있습니다.

회사는 C# WinForms 기반 입학전형 프로그램을 웹으로 전환하기 시작했습니다. 그 과정에서 성적산출 영역이 분리되었고, 제가 해당 시스템을 맡았습니다.

두 시스템은 함께 구성된 제품입니다. 입학전형시스템에서는 팀 프로젝트의 보고·업로드·연계 기능 개발에 참여했고, 별도 개발 프로젝트로 분리된 성적산출 시스템은 요구사항부터 구현까지 맡았습니다.

교차검증을 거쳐 실제 입시에 적용

2025년 12월 개발을 시작했습니다. 2026학년도 정시에는 약 10개 대학의 수능성적 계산을 기존 시스템과 교차검증하는 데 활용했습니다. 현재는 2027학년도 수시 내신성적 계산에 4개 대학이 사용하고 있습니다.

자료 수신부터 결과 확인까지

학생부·수능 자료 수신, 산출, 검증, 출력을 개발했습니다. 대학과 모집시기별 자료를 관리하고, 입학전형 관리시스템과 원천 자료·산출 결과를 주고받도록 연결했습니다.

여러 지원자의 결과를 검증하는 화면

화면 설계와 Next.js 프론트엔드 구현도 직접 담당했습니다. 목록과 상세 화면을 왕복하지 않고 학생별 계산 근거를 확인하게 했으며, 여러 학생을 비교할 때는 전체 목록형으로 전환할 수 있게 했습니다.

보정된 점수는 원래 산출점수·적용점수·변경 사유를 구분해, 담당자가 현재 점수의 근거를 함께 확인하도록 설계했습니다. 동시 수정은 버전 검사와 DB 잠금으로 보호하고, 원천 자료가 삭제돼도 보정 사유와 변경 이력이 남도록 구현했습니다.

대학별 요구와 공통 처리의 경계

대학별 산식 변경이 공통 자료 처리에 영향을 주는 범위를 줄이기 위해, 학생부 계산 로직과 자료 조회·저장을 분리했습니다. 수능은 산출 설정과 환산표를 기반으로 처리하도록 구성했습니다.

개발 이후 현재까지 유지보수·개선 개발을 이어가고 있습니다. 학교별 추가개발·유지보수와 운영은 부서 운영자·동료 개발자들과 함께 진행합니다.

02 · 입학전형입학전형시스템
팀 프로젝트 개발 참여

접수 현황이 바뀌어도 출력 당시의 기록은 보존

입학전형시스템의 웹 전환에 참여해, 현재 접수 현황과 이미 출력한 보고서를 구분해 관리하도록 설계·개발했습니다. 업로드 결과 확인과 자료 일괄 수정도 맡았습니다.

성적산출 시스템과 함께 구성된 제품으로, 2027학년도 수시에 사용 중입니다.

업무 문제
늦게 수신된 원서가 추가되면 같은 날짜의 집계도 달라집니다. 현재 현황과 이미 출력한 보고서를 구분해야 했습니다.
설계 판단
출력 당시의 결과를 스냅샷으로 보존하고, 변경된 결과는 새 버전으로 남겼습니다.

학교별 접수처·전형·모집단위별 일계·누계와 경쟁률을 화면·Excel·PDF로 제공했습니다. 현황을 갱신해도 이전 보고서의 수치를 확인할 수 있도록 구성하고, 충원 보고의 합격 통보·등록·포기·환불 상태와 보고구간별 집계 기준을 정리했습니다.

함께 담당한 기능

수능최저 연동
결과 수신 → 수험번호 매칭·미리보기 → 저장 → 사정제외 반영을 연결했습니다. 이미 다른 사유로 제외된 지원자는 덮어쓰지 않도록 처리했습니다.
후보 인원 설정
최초합격자 최종심사에서 모집단위별 후보 인원을 설정하도록 개발했습니다. 변경 사유·이력과 동시 수정 검사를 연결하고, 재선발 전에는 최종 마감을 차단했습니다.
업로드·자료 수정
파일별 성공·실패·미확인을 실행 이력으로 구분했습니다. 일괄 수정은 미선택 필드·다른 서비스 자료를 보존하고 500건 단위로 저장·롤백하며, 앞서 성공한 묶음은 유지합니다.
개인정보·연계
서버에서 동일인을 비교하고 권한·감사 기록을 확인하는 출력 경로에 연결했습니다. 외부 전달용 서비스·용도별 가상 식별키와 성적산출용 대량 학생부 반출 경로를 구현했습니다.

03 · 배포 전환이전 팀
부서 전체 솔루션

두 운영 환경을 k3s·Argo CD로

부서 최초 k3s 애플리케이션 이관을 주도하고, 모든 솔루션 프로젝트의 k3s·Argo CD 전환을 이끌었습니다.

클러스터 구축: 시스템부서애플리케이션 이관·배포 전환·확산: 구성우

Linux·PM2 → k3s: Linux 서버에서 PM2로 운영하던 애플리케이션을 k3s로 옮겼습니다.

k8s → k3s: IDC 이전에 맞춰 기존 Kubernetes에서 운영하던 애플리케이션을 새 k3s 환경에 이관했습니다.

1. Bitbucket빌드 번호로 이미지 태깅
2. GitOps 저장소배포 이미지 버전 갱신
3. Argo CDAutoSync로 설정 반영
4. k3s지정 버전 서비스 배포

배포 설정 재사용과 기술공유로 부서 전체에 적용

파이프라인이 GitOps 매니페스트의 이미지 버전을 갱신하도록 연결하고, 빌드 환경변수 처리와 설정 갱신 단계를 모듈화해 다른 배포 환경에도 적용했습니다. k3s 이관 기술공유 세션을 진행하며 프로젝트별 적용을 이끌었고, 부서 내 모든 솔루션 프로젝트가 k3s·Argo CD 방식으로 전환했습니다.

애플리케이션과 연결된 운영 환경도 이관

출결 서비스의 이관에 맞춰 Azure 파일 저장 공통 모듈을 만들고 업로드·다운로드 경로를 전환했습니다. 도메인·인증 연동 서버를 이관하고, 논술 서비스의 로그 수집 경로도 k3s 운영 환경에 맞췄습니다.

k3s · Argo CD · Bitbucket Pipelines · Azure Storage

04 · 성능 개선성적산출 시스템
저장 경로 개선

계산 로직을 유지하며 저장 경로 개선

단계별 실행 시간을 측정해 스냅샷·산출 결과·과목 상세 저장을 병목으로 특정하고, 저장 경로를 중심으로 개선했습니다.

단계별 측정으로 개선 대상을 좁혔습니다

전체 산출 과정의 실행 시간을 나눠 확인해 저장 구간을 개선 대상으로 잡았습니다. 스냅샷 저장부터 변경하고, 과목 상세와 최종 결과 저장 순으로 확대하며 각 변경의 효과를 확인했습니다. 계산 규칙·산출 대상·트랜잭션 순서는 유지했습니다.

AI 활용과 변경 범위 결정

코드 분석·구현·검증에 Codex를 활용했습니다. 광범위한 리팩터링안은 적용하지 않고, 측정에서 확인한 저장 병목으로 변경 범위를 한정했습니다.

저장 방식 변경과 데이터 처리 조건

Prisma createMany를 파라미터 바인딩 PostgreSQL JSONB 일괄 삽입으로 교체했습니다. 과목 상세는 최대 8,000행씩 나눠 저장하고, 비정상 점수가 JSON 변환 중 null로 바뀌는 경우를 차단했습니다.

변경 후 확인한 범위

변경 전후 산출 결과·실패·과목 상세의 건수 일치와 관련 집중 테스트·빌드 통과를 확인했습니다. 후속 검증에서는 실제 PostgreSQL에 저장한 뒤 필드별로 다시 조회해 JSONB 매핑을 확인하고, 비정상 점수가 해당 지원자의 실패로 격리되는지도 검증했습니다.

05 · 데이터 연계입학전형 관리 ↔ 성적산출
송신·수신 경로 구현

학생부 자료를 스트리밍으로 전달

일반 조회의 10만 행 제한을 해결할 전용 경로를 만들고, 수신 완료를 확인한 자료만 사용 데이터로 교체하도록 했습니다.

성적산출 시스템에 학생부 자료를 넘겨야 했지만, 일반 조회에는 행 수 제한이 있었고 대형 JSON 응답에도 제약이 있었습니다. PostgreSQL COPY로 추출한 CSV를 gzip으로 압축해 전송하도록 바꿨습니다.

1. COPYPostgreSQL 추출
2. CSV · gzipHTTP 전송
3. 임시 적재SQLite 수신
4. 검증 후 교체완료 상태·행 수 비교

덜 받은 자료가 반영되지 않도록

학생정보·교과·출결을 각각 임시 테이블에 받았습니다. 송신 측 완료 상태와 기록된 행 수가 로컬 적재 건수와 일치할 때만 교체했습니다. 중단, 행 수 불일치, 압축 데이터 절단 시에는 기존 자료를 유지했습니다.

진행 상태: 전용 송수신 경로 구현 및 로컬 검증 완료.
